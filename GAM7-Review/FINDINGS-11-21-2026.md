the real crashes that exist.** I had no Google credentials and no access to
your work computer, so no command was run against a real Google tenant. What I
could do is check the code against Google's own API descriptions. That
catches the crash types that happen *before* Google ever answers:

I proved the checking tool works by seeding four deliberate mistakes into a
scratch copy of GAM (misspelled method, misspelled resource, bogus argument,
deleted required argument). It caught all four.

**What this does NOT prove:** behavior that depends on real data or on what
Google's servers return (permissions, quotas, field contents, new server-side
rules). Only running commands against a real tenant can test those. See
"What I could not do" at the end.

### Goal B: "completely uses all of Google's API"

**Not achieved, and it cannot responsibly be achieved in an unattended review.**
Google publishes 316 APIs (528 versions in all). GAM uses 47 of Google's live
API documents plus 4 that ship inside GAM, plus 2 legacy GData APIs (Contacts
and Email Audit) that have no document - in other words the Workspace and
Cloud Identity administration surface. GAM is a
Workspace administration tool, so most Google APIs (ads, maps, Play, Firebase,
...) are correctly out of scope. What I did instead:

1. Measured exactly what is covered and what is not (section 4).
2. Identified the Workspace-relevant APIs GAM does not use at all (section 4).
3. Produced a complete method/scope outline for the most plausible ones, so
   adding a command is a matter of coding, not research
   (`09-Reports/candidate-new-apis-11-21-2026.md`).

I did **not** write new GAM commands. Reasons: they cannot be tested without a
Google tenant, GAM has strict conventions across an 84,000-line file, and
untested code in an admin tool is a risk, not an improvement. I also have no
push access to GAM-team/GAM, so any upstream change needs your decision.

## 2. Real bugs found (both fixed in `07-Patches`)

### Bug 1 - `gam update vaulthold` can never update a hold  (patch 0001)

* Where: `doUpdateVaultHold`, `src/gam/__init__.py` line 45811
* The call passed `throwReas=[...]` (typo for `throwReasons=`). GAM's call
  wrapper forwards unknown names to Google's client library, which rejects
  them:
  `TypeError: Got an unexpected keyword argument throwReas`
* Effect: whenever the command actually had a change to send, it aborted
  instead of updating the hold. It also meant the intended handling of
  not-found / forbidden / permission-denied errors never ran.
* Proof: reproduced with the real client library and Google's real Vault
  description (output captured in the work log in CLAUDE-NOTES.md).
* Fix: `throwReas` -> `throwReasons` (one word).

### Bug 2 - Classroom "remove items" retry crashes  (patch 0001)

* Where: `_batchRemoveItemsFromCourse`, line 53537 (the retry after a quota or
  service-unavailable error)
* The retry called the delete method with `body=rbody`. Classroom's
  students/teachers/aliases/topics/announcements `delete` methods take
  `courseId` plus `userId` / `alias` / `id` and **no body**.
  The result is GAM stopping with
  `ERROR: Got an unexpected keyword argument body`
  right when it was supposed to retry. It only happens on the retry path, so it
  would show up only during busy periods or with large removals.
* Proof: ran GAM's own `callGAPI` against a real Classroom client with a mocked
  HTTP answer: old argument shape -> GAM aborts with that error; new shape ->
  success.
* Fix: `body=rbody` -> `**rbody` (the dictionary already holds
  `{userId|alias|id: value}`).

### Hardening - patch 0002 (not crashes; security and robustness)

* **SQL built by string pasting** in the gcloud re-authentication path
  (`runSqliteQuery`): the admin email was pasted into the SQL text. Changed to
  a bound `?` parameter, and the connection is now always closed. Tested with
  a real temporary SQLite database, including an injection-style value.
  Practical risk was low (the value comes from your own token), but there is no
  reason to keep it.
* **MD5 on FIPS systems**: `hashlib.md5()` raises `ValueError` on a
  FIPS-enabled computer. It is only used to compare a downloaded file with
  Drive's `md5Checksum` (integrity, not security), so
  `usedforsecurity=False` is correct and prevents that crash.
* Other bandit hits examined and **left alone** as safe: `os.system('clear')`
  (constant string), and the self-update archive extraction (already validated
  for zip, and tar uses `filter='data'`).

Both patches apply cleanly, in order, to upstream HEAD `30449fc`
(`git apply --check` verified). After applying 0001 the audit reports zero
bad-argument findings.

## 3. Items that need a human decision or a real-tenant check

1. **Cloud Channel read-only scope.** GAM's client-scope table asks for
   `https://www.googleapis.com/auth/apps.order.readonly` for the Cloud Channel
   API (via its "readonly" option). Google's description lists only
   `apps.order` and `apps.reports.usage.readonly` for Cloud Channel. If that
   read-only scope does not exist, choosing the read-only variant in
   `gam oauth create` would ask Google for an unknown scope and the
   authorization could be rejected. The entry is `offByDefault`, so it only
   affects people who tick it. I could not test it. Also note the unrequested
   scope `apps.reports.usage.readonly` (the Cloud Channel reports).
   Reseller (a different API) legitimately has `apps.order.readonly`.
2. **Email Audit API (`gam create/delete/show monitor`).** It has no discovery
   document (legacy GData API) and Google's developer site was blocked from
   this sandbox, so I could not confirm whether Google still serves it. If it
   has been shut down, those commands would fail with an HTTP error and
   should be removed or re-pointed.
3. **Contacts API v3 (domain shared contacts)** - same situation: legacy
   GData, no discovery document, could not verify.
4. Four scopes the tool first flagged are fine (Google's descriptions are
   incomplete): `business.manage`, both `datastudio` scopes, and the
   intentional Drive pairing for Drive Activity. They are recorded as known
   exceptions in `06-OAuth-Scope-Audit/audit_oauth_scopes.py`.

## 4. API coverage

(Full tables: `09-Reports/run-11-21-2026_04-14/api_coverage_report.md`.)

**Important caution about the numbers.** GAM often reaches an API through
helper functions or tables of resource names, so the static scan can only tie
some calls to an API with certainty ("strict"). The "called" counts are
therefore **lower bounds**. Example: Tag Manager shows 0 strict calls but GAM
does have Tag Manager commands, built from data tables. Use the lists as
leads to verify, not as proof that something is missing.

### 4a. Google APIs GAM already uses

Strict calls found, a selection (strict / total methods Google offers):
Directory 92/128, Gmail 38/79, Cloud Identity v1 38/70, Vault 23/33,
Classroom 28/105, Chat 26/56, Chrome Management 21/71, Drive v3 17/64,
People 16/24, Reseller 13/17, Meet 8/24, Alert Center 8/11, Data Transfer
4/5, Reports 3/6, ... The remaining methods in each API are features Google
offers for which GAM has no command (or reaches them in a way the scan cannot
see). Section 5 of the coverage report lists them per API.

### 4b. Calls to deprecated methods

**None found.** The drive `teamdrives` methods and Analytics
`conversionEvents` (both deprecated by Google) are not called; GAM already
uses `drives` for shared drives.
(The first run of my tool reported them by mistake; that was my loose
matching, since corrected. See CLAUDE-NOTES.md.)

### 4c. API version currency

Every version GAM uses exists in Google's directory. Where GAM is not on
Google's "preferred" version, the reasons I could confirm are:
* `iam v1`: Google's preferred `iam v2` contains only the `policies` resource
  (I checked), so GAM correctly stays on v1 for service accounts and keys.
* The two Cloud Identity `...beta1` entries: GAM's code switches to the beta
  API only when a command asks for fields the v1 API lacks (for example
  `externalIds`).
* `alertcenter` (v1beta1) and `analyticsadmin` (v1beta): Google publishes only
  alpha/beta versions of these, so there is no stable version to move to.
* `drive2` and `cloudresourcemanagerv1`: GAM keeps these older versions on
  purpose or for compatibility; I did not verify the exact reason, so treat
  this as something to confirm with the GAM maintainers rather than a defect.

### 4d. Workspace-relevant Google APIs GAM does not use at all

| API | Version | Why an administrator might want it |
|---|---|---|
| appsmarket | v2 | Inspect Marketplace apps / licenses installed in the domain |
| script (Apps Script) | v1 | Manage/deploy script projects, view execution metrics |
| slides | v1 | GAM has Docs, Sheets and Forms but not Slides |
| workspaceevents | v1 | Subscriptions to Drive/Chat/Meet events |
| gmailpostmastertools | v2 | Domain reputation, spam rate, SPF/DKIM/DMARC delivery stats |
| cloudsearch | v1 | Cloud Search data/identity sources |
| dataportability | v1 | Export a user's data (offboarding, legal requests) |
| chromewebstore | v2 | Inspect/publish Chrome extension items |
| verifiedaccess | v2 | Chrome Verified Access (Zero Trust attestation) |
| androidmanagement, androiddeviceprovisioning | v1 | Android Enterprise devices / zero-touch |
| cloudasset, logging, securitycenter | v1/v2 | Google Cloud security and audit data |
| mybusinessbusinessinformation, marketingplatformadmin | v1/v1alpha | Business profile and marketing platform admin |

Complete method lists and the OAuth scopes for the first nine are in
`09-Reports/candidate-new-apis-11-21-2026.md`.

My suggested order if you want GAM extended (best value for a network-security
and user-experience focus): **Gmail Postmaster Tools** (email authentication
and spam reputation is directly security relevant), **Workspace Marketplace**
(which third-party apps are installed), **Data Portability** (offboarding),
**Apps Script** (find risky scripts), then **Slides** / **Workspace Events**.

## 5. Smaller observations (no action required, recorded for completeness)

* Legacy code in `atom/` and `gdata/` has Python-2 leftovers that pyflakes
  flags (`cmp`, `unicode`, an undefined `url_params` in `GetMedia`,
  `CLIENT_LOGIN_SCOPES`). I traced them: they sit in functions GAM's OAuth
  path does not call (for example `Url.__cmp__` is never used by Python 3), so
  they are latent rather than active bugs. Removing the dead code would be a
  clean-up, not a fix.
* `gam/meet-v2beta.json` ships in the package but nothing references it
  (GAM uses the live Meet v2 description). Harmless dead file.
* A few `nonlocal` / `global` statements are unused (cosmetic).
* The self-update uses `tar.extractall(..., filter='data')`; the `filter`
  argument only exists in Python 3.10.12 and newer, so on an older 3.10 patch
  release the self-update (not normal commands) would hit a `TypeError`.
* `gam checkconn` failed in my sandbox on a TLS certificate check; that was
  the sandbox's proxy certificate, not GAM.

## 6. What I could not do (please read)

* Run any command against a real Google Workspace tenant (no credentials and,
  as you said, no access to your work computer). Anything that depends on real
  data, permissions, quotas, or server-side behavior is untested.
* Test `Run-All-Audits.bat` on Windows. It was written carefully and is a
  line-for-line twin of `run_all_audits.sh`, which I did run successfully on
  Linux. Test it once before relying on it.
* Reach `developers.google.com` (blocked from the sandbox), so I could not read
  Google's own notices about the Email Audit and Contacts APIs.
* Push anything to GAM-team/GAM or change your GAMGUI project. The GAMGUI
  repository (`GuruGabe/GAM-GUI-Overlay`) was **not** reviewed.
* Guarantee that Google will not change an API tomorrow. These tools exist so
  the check can be repeated in minutes whenever GAM is updated or Google
  changes something.
